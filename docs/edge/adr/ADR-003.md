# ADR-003 — Keycloak Clients & Vertical Mapping

## Status

Accepted (P0-A lock)

## Context

ERP clients in `platform` realm: `platform-api`, `platform-admin`, `platform-web`, `platform-b2c`. Edge needs browser PKCE + confidential service-account access, plus a durable mapping from Keycloak Organization → Edge vertical.

## Problem

Without dedicated clients and an explicit mapping store, vertical membership would be inferred from JWT alone or wrongly from ERP org tables.

## Options considered

| Option | Summary |
|--------|---------|
| A | Reuse `platform-web` / `platform-api` with extra scopes |
| B | Edge clients inside `platform` realm |
| C | `edge-admin` realm; clients `edge-admin-api` + `edge-admin-web`; KC Org ↔ vertical; mapping in Control Plane |

## Decision

**Option C:**

| Client | Type | Use |
|--------|------|-----|
| `edge-admin-api` | Confidential, service account | Nest Edge module ↔ KC Admin API; audience for Edge APIs as designed |
| `edge-admin-web` | Public, PKCE | Edge console browser login |

**One Keycloak Organization in `edge-admin` = one Edge vertical.** Canonical mapping rows live in **Control Plane** (Edge tables), not in ERP `organizations`.

## Rationale

Mirrors ERP’s successful pattern (app DB validates KC org membership) without sharing tables (constraint 6). Public PKCE client matches frontend 1A.

## Security implications

- Redirect URIs limited to Edge console paths.  
- SA secret never shipped to browser.  
- Constraint 3: azp/audience of Edge tokens never accepted by ERP `AuthGuard`/`PermissionGuard`.  
- Constraint 5: mapping + membership checked server-side.

## Operational implications

- Realm export must include org-enabled flag and bootstrap vertical orgs as needed.  
- Secret rotation for `edge-admin-api` independent of `platform-admin-secret`.

## Data implications

CP mapping table (name TBD in 073+), e.g. `edge_verticals(id, keycloak_organization_id, slug, status, …)`.

## Migration implications

P0-B realm + P0-C mapping schema; backfill only for Edge-created verticals.

## Rejected alternatives

- **A/B:** Client or realm reuse — breaks constraints 1 and 3; confuses Org Switcher semantics.

## Consequences

- Frontend uses dedicated Edge client env (ADR-016).  
- Reconcile job syncs KC orgs ↔ `edge_verticals` (ADR-010).

## Acceptance criteria

- [ ] Both clients present in `edge-admin` realm export.  
- [ ] CP mapping unique on `keycloak_organization_id`.  
- [ ] ERP `organizations` table unchanged and unused by Edge authz.

## Mandatory constraints

1–6; especially 3 and 6.
