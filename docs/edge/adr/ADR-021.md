# ADR-021 — Product Tenant Cardinality & Multi-Establishment Boundary

## Status

Accepted (RGOM alignment lock — 2026-11-17)

## Context

La doctrine commerciale et le RGOM imposent :

- un client achète un **produit vertical** (Syntix Pharma, Okapi Restaurant, …) ;
- un **Product Tenant** Edge est lié à un seul produit ;
- un compte / groupe multi-activités peut posséder **plusieurs** Product Tenants ;
- le Business Backend exécute le métier **dans** ce tenant.

Confusion observée : les tests BB `multi-vertical` (pharmacy + restaurant + … sous un même tenant) ont pu être lus comme « multi-produits dans un tenant ». Ce n’est **pas** le modèle de production.

Le besoin métier réel est : **plusieurs établissements** (ex. plusieurs restaurants) sous **un** tenant produit, chaque établissement étant une **organization** Keycloak/BB, un utilisateur pouvant appartenir à une ou plusieurs organizations du **même** tenant.

## Problem

Sans règle explicite :

1. risque de fusionner plusieurs produits verticaux dans un même tenant ;
2. confusion Account CRM ↔ Product Tenant ↔ Organization ;
3. quotas, entitlements et facturation incorrects ;
4. tests lab pris pour contrat de production.

## Options considered

| Option | Summary | Verdict |
|--------|---------|---------|
| A | 1 tenant = N produits verticaux | Rejected — viole RGOM / packaging / entitlements |
| B | 1 Product Tenant = 1 produit ; N orgs = N établissements du même produit | **Selected** |
| C | 1 org = 1 tenant toujours | Rejected — coûteux, casse multi-sites et consolidation |

## Decision

**Option B.**

### Règles non négociables

| # | Règle |
|---|--------|
| 1 | `Product Tenant` Edge ↔ exactement **un** `product_id` vertical |
| 2 | BB Tenant runtime = Product Tenant Edge (même identité / binding) |
| 3 | `Organization` (Keycloak + BB) = établissement / site / branche **du même produit** |
| 4 | Un user peut appartenir à **1..N organizations** du **même** tenant |
| 5 | Un groupe multi-activités (pharmacie + restaurant) = **N Product Tenants** (N abonnements) |
| 6 | Multi-environnement (staging/prod) uniquement via `environment_slot` explicite (voir P7 DELTA-01) — défaut : un tenant actif par account+product |
| 7 | Les Business Profiles / packs BB sont **intra-produit** (Retail vs Wholesale dans Syntix) — jamais un second produit concurrent sous le même tenant en production |

### Modèle

```text
Commercial Account (CRM P4)
│
├── Product Tenant A (product = Syntix Pharma)
│     ├── Subscription (temporelle) + Entitlements
│     └── BB Tenant A
│           ├── Org = Pharmacie Centre
│           ├── Org = Pharmacie Nord
│           └── User U ∈ Org Centre et/ou Nord
│
└── Product Tenant B (product = Okapi Restaurant)
      └── BB Tenant B
            ├── Org = Restaurant Centre
            └── Org = Restaurant Aéroport
```

## Rationale

- Aligne commercialisation par verticale, catalogue, plans et entitlements.
- Permet multi-sites / multi-caisses / multi-entrepôts sans multiplier les produits.
- Préserve isolation et facturation propre pour les groupes multi-activités.

## Consequences

### Positives

- Quotas (`max_organizations`, `max_users`, …) mesurables et facturables.
- Expansion = add org / upgrade plan / add-on — pas fusion de verticales.
- Mapping clair Edge control/v1 ↔ BB.

### Négatives / travail requis

- Refactor des helpers/tests BB « five-vertical under one tenant » → multi-establishment **same product** + tests cross-tenant.
- Contract-cadre groupe éventuel reste au niveau Account/Contract Edge, **sans** fusionner les tenants.

## Security implications

- Pas de cross-product data plane dans un même tenant production.
- Org switch reste scopé au tenant produit.
- Entitlements tenant-level ; permissions user/org séparées (RBAC ≠ entitlements).

## Operational implications

- Provisioning Edge doit pousser `product_id` + entitlements non vides.
- Ready = entitlements appliqués + org initiale + checks métier min.
- Monitoring drift Edge↔BB sur projection entitlements.
