# ADR-001 — Domain Boundaries: Platform / Vertical / Product / Tenant / BusinessOrg

## Status

Accepted (P0-A lock)

## Context

Okapi today ships an ERP Platform Core (Nest modular monolith + `edge-frontend` shell) where **Tenant** and **Business Organization** are first-class, JWT-scoped concepts. Edge Admin must operate **vertical workspaces** for platform operators without collapsing those concepts into ERP tenancy.

## Problem

Without explicit vocabulary, implementers will overload `tenant_id`, Keycloak Organizations, and Org Switcher for Edge verticals — creating cross-domain authz and data leaks.

## Options considered

| Option | Summary |
|--------|---------|
| A | Treat Edge vertical ≡ ERP tenant |
| B | Treat Edge vertical ≡ ERP business org (reuse Org Switcher) |
| C | Distinct taxonomy: Platform, Vertical, Product, Tenant, BusinessOrg |

## Decision

**Option C.** Maintain five distinct concepts:

| Term | Meaning | SoT (P0) |
|------|---------|----------|
| **Platform** | Okapi control/ops capability hosting Edge Admin + ERP | Deployment + CP |
| **Vertical** | Edge-administered industry/workspace line (KC Org in `edge-admin`) | Edge CP + KC |
| **Product** | Packaged capability sold/enabled inside a vertical or tenant | Catalog (later) |
| **Tenant** | ERP customer isolation boundary (`tenant_id` JWT) | ERP CP + JWT |
| **BusinessOrg** | ERP org inside a tenant (Org Switcher) | ERP CP + KC `platform` |

Frontend vertical ID is a **selector only**; backend membership + session are authoritative.

## Rationale

Preserves ERP invariants already enforced (`JwtValidationService` requires `tenant_id`; `TenantContextService`) while giving Edge a clean workspace model (ADR-007).

## Security implications

- Prevents confused-deputy: ERP tokens cannot imply Edge vertical admin, and vice versa.  
- Constraint 4: `tenant_context` ≠ `vertical_workspace_context`; never merge middleware.  
- Constraint 5: backend authority for vertical access.

## Operational implications

Docs, metrics, and runbooks must label streams by domain. On-call must not treat Edge outages as tenant DB incidents by default.

## Data implications

Edge entities reference `vertical_id` (opaque UUID), never reuse ERP `tenants.id` as Edge workspace PK. Mapping tables may *associate* products/tenants later without identity merge.

## Migration implications

No data migration of ERP tenants into Edge verticals in P0. New CP tables only (ADR-009).

## Rejected alternatives

- **A/B:** Collapse vertical into tenant/org — violates constraints 1 and 4; would force Org Switcher into Edge chrome (rejected by 1A).

## Consequences

- Every Edge ADR must use this vocabulary.  
- APIs under `/api/v1/edge/**` speak vertical/workspace, not tenant/org switch.

## Acceptance criteria

- [ ] Glossary published and referenced by ADR-002…020.  
- [ ] No Edge API accepts `tenantId` as workspace authority.  
- [ ] ERP Org Switcher remains ERP-only (COMPATIBILITY.md).

## Mandatory constraints

1. No ERP regression  
2. Strict session separation  
3. Strict Keycloak client separation  
4. Strict context separation  
5. Backend authority  
6. Coexistence via adapted contracts
