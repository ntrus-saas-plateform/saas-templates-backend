# ADR-011 — Edge Invitations (Hashed, Single-Use, Edge Tables)

## Status

Accepted (P0-A lock)

## Context

ERP invitations: `migrations/control-plane/009_invitations.sql` with `token_hash`, statuses `PENDING|ACCEPTED|EXPIRED|REVOKED`, tenant/org scoped APIs under identity module.

## Problem

Reusing ERP invitation rows would require `tenant_id` / `organization_id` and pull Edge onboarding into ERP invite UX and email templates incorrectly.

## Options considered

| Option | Summary |
|--------|---------|
| A | Reuse `invitations` table with nullable tenant |
| B | Plain-text tokens in Edge DB |
| C | Edge-specific tables; hashed single-use tokens |

## Decision

**Option C.** Edge invitations live in **Edge-specific CP tables**. Store **only token hashes** (e.g. SHA-256); raw token shown once. Single-use: accept transitions to terminal status; retries fail. TTL required. Ties to admin lifecycle `INVITATION_PENDING` (ADR-004).

## Rationale

Proven ERP pattern adapted without domain mix (constraint 6).

## Security implications

- Enumerate-resistant tokens (≥128 bits entropy).  
- Rate-limit accept endpoints.  
- Constraint 1: ERP invitation APIs/tables unchanged.

## Operational implications

Separate email templates / deep links into `(edge-console)` accept route.

## Data implications

`edge_invitations` with `token_hash UNIQUE`, vertical target, roles to grant, invited_by, expires_at.

## Migration implications

073+; no ALTER on `invitations`.

## Rejected alternatives

- **A:** Shared table — breaks ERP invariants and constraint 6.  
- **B:** Plain-text — disclosure risk in backups.

## Consequences

- Accept flow creates/activates Edge admin + membership (ADR-005) transactionally.  
- Reconcile must not invent invitations (ADR-010).

## Acceptance criteria

- [ ] Raw token never persisted.  
- [ ] Second accept fails.  
- [ ] ERP invite e2e still green.

## Mandatory constraints

1, 5, 6.
